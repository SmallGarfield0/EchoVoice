# EchoVoice 高性能实时屏幕共享系统重构设计方案

**第一轮架构评审稿 · 2026-11-20**　审计基线 `7777c2335d089997848a0745a5d57d859f9152a1`。文中源码位置均相对于仓库根目录。现状来自代码检查、仓库历史测量和一次本机浏览器回环，三者在下文分别标明。所有新阈值均为待验证的工程起点。

## 1. 建议批准的路线

保留现有按需观看、每位观看者一条 WebRTC 连接、内建 TURN 和共用的浏览器观看端。第一批工作应让团队能回答三个问题：**屏幕变化到显示到底多久，哪一个环节占掉帧预算，网络恢复后多久回到实时画面**。当前代码已经给出两个优先于更换编解码器的问题：原生回读链上的像素与时间戳错位，以及观看端缓冲控制器的运行路径断裂。

建议批准三个可分别回退的实验：① 修正时间基准并建立物理端到端基线，② 在同一块显卡上对比现有 WGC 回读路径和 D3D11 纹理直送硬编路径，③ 对比现有 RTT 阶梯和以实际抖动、冻结及帧龄驱动的交互播放策略。第一项是后两项的测量前提。1080p60 是第一道发布门槛。1440p60 与 4K 按设备组合开放。SFU、厂商专用编码 SDK、原生解码器、远控 DataChannel 均有独立的投入判断条件。

**当前控制器边界。** 原生 PLI/FIR 合并并限频，默认 interceptor 处理 NACK 等反馈；码率控制器基于 REMB 留余量、处理估计过期、受压下降和逐步上探。`main.rs:1889,3291` 显示任一观看者的视频队列溢出均可触发共享主码率下降，即使压力来自低档。Web 依靠浏览器内置拥塞控制，并在每个 sender 上设置上限；按总像素吞吐优先排列 H.264 是启发式排序，不能认定已经使用硬编。独立评测总上行饱和和单一差链路，才能判定该降哪一层。

**保留**帧泵、按需建链、低档按需开启、压缩帧引用共享、控制面权限、ICE 恢复、窗口关闭处理和预览/观看 UI 的入口。**优先替换**回读时钟绑定、无帧龄约束的排队方式、播放预算公式及仅凭枚举开放档位的能力判断。历史 SFU 文档的“原生单编码层”描述有版本差异，当前代码已有两档 H.264 独立编码；这是应用层选流，和单个 RTP sender 的标准 simulcast/SVC 应分别测试。

## 3. 拟议系统边界

| 模块 / 接口 | 所有权、数据和失败边界 |
|---|---|
| CaptureSource → FrameProcessor | 每个发布会话持有一个采集源。帧携带 session/generation、序号、源单调时间、尺寸、色域/范围、旋转、适配器 LUID、纹理租约或 CPU 平面。回调快速交还源帧，不让网络持有帧池对象 |
| FrameProcessor → Encoder | 按实际订阅生成目标层的 NV12 表面或 CPU 平面；每层有最新待处理帧、有限在途表面和完成信号。适配器/尺寸/色域代次变化时暂停提交、回收旧表面，切到新代次 |
| Encoder → Publisher | 每个编码输出携带层、源帧号、原始采集时间、媒体 PTS、关键帧标志、实际 codec/profile 和参数集。可查询能力、设置目标码率、请求 IDR、受控重建。用户配置和当前生效参数分别保存 |
| Publisher → PeerSession | 原生按兼容格式和层复用压缩帧；每个观看者独立管理 SDP、SSRC、包历史、pacing、网络预算、写操作和停止标记。Web 把轨交给浏览器，应用设置约束并读取实际执行结果 |
| Receiver → Renderer | RTC 接收器独占解抖、解码与 A/V 同步；视频元素、全屏和浮窗复用现有绑定。渲染观测以帧呈现回调和播放统计为主，保留物理显示测量入口 |
| QualityController / Diagnostics | 按会话、层、peer、SSRC 和采样区间读取不可变快照，输出带原因和有效期的码率/选层/采集建议。采样与 UI 绘制在媒体热路之外 |
| RemoteAssistance | 依赖共享身份、有效订阅和已批准的控制租约；只接收会话事件和输入。控制失败仅终止控制会话 |

会话由创建、运行、重配、停止、结束/失败组成。停止时先禁止新回调，关闭订阅与写任务，取消采集/编码工作，释放音频和纹理池，再确认资源回收；处理取消、重复停止、迟到的 answer/ICE/编码输出。所有异步结果带代次。MFT 卡住时须验证取消是否能唤醒等待，限制重建次数；本地权限或目标丢失时以实际失败原因结束。UI 使用已有控制器和双语文案，`App.svelte` 只接线。

## 5. Windows 采集、颜色与硬件编码

**窗口优先使用 WGC，显示器同时评测 WGC 与 Desktop Duplication。** 在同源、同显卡、同编码器下，仅切换采集后端，分别测帧到达延迟、遗漏更新、采集线程 P99、GPU 占用、首帧和静止后首个变化。DXGI 测 dirty/move rect、光标独立更新、旋转屏、`ACCESS_LOST` 后重建。高运动时脏区可能接近整屏，届时整纹理转换更便宜；稀疏更新可跳过重复工作，但指针移动和最后一帧必须送达。窗口共享始终保持已选窗口的范围。显示器回退须记录原因，静态画面不得单凭无新帧就判采集死亡。[Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) · [Microsoft WGC](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture)

**同适配器 GPU 路径。** 在采集设备所在 LUID 上，保留一张最新待用纹理 → D3D11 video processor 或 shader 完成裁切、等比缩放和 BGRA→NV12 → 从有限纹理池取得表面 → 用 DXGI surface buffer 构造 MF sample，向支持 D3D11 的 MFT 关联 DXGI device manager → 编码完成后归还。在途池起测 2–3 张，实际深度以驱动要求和 P95 帧龄裁定；禁止持有 WGC 帧跨越整个网络发送过程。忽略过期帧时仍交回资源。若必须做一次 GPU 内拷贝换取及时释放采集帧，可接受并计数。无 CPU 映射只能证明应用路径消除了读回，驱动内部搬运还需 ETW/引擎跟踪验证。双显卡单独测跨 LUID、切换主显、HDR 开关、设备移除与重连。无法提交纹理时走明示的同质量内存路径，或报告设备无法持续达到所选档位。[Microsoft DXGI Surface Buffer](https://learn.microsoft.com/en-us/windows/win32/api/mfapi/nf-mfapi-mfcreatedxgisurfacebuffer) · [MFT D3D11 能力属性](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-sa-d3d11-aware)

**尺寸和颜色。** 全程使用物理像素和实际内容矩形，高 DPI、负坐标、多显示器和黑边映射只换算一次；窗口 resize 时增加代次。首版交付 SDR BT.709，显式记录 nominal range、矩阵和 transfer，黑白阶、肤色、彩色小字和灰阶图同时测。HDR 源优先以支持的高精度格式采集再显式 tone-map 到 SDR；端到端 HDR/P010/10-bit 需采集、编解码、信令与显示全部通过，不能把 BGRA8 标为 HDR。4:2:0 的彩色细线有物理分辨率损失，在运动/文字质量比较中单列。

| 编码候选 | 试验与开放条件 | 工程取舍 |
|---|---|---|
| H.264 / 硬件 MFT | 首选跨端路径。对 NVENC、AMF、Intel Quick Sync 对应设备分别记录 adapter、MFT 名称、驱动、真实尺寸/FPS、可用并发实例；用实际帧试编、验 SPS、首 IDR、编码耗时和对端解码 | MFT 优先覆盖三厂。同尺寸比较内存输入与纹理输入；先验证 1080p60 和 1440p60。只有 MFT 无法暴露必要能力且专用 SDK 有可复测优势，才引入对应后端 |
| H.264 / OpenH264 | 保留 CPU 路径覆盖兼容档，基于持续吞吐判断能否兑现原请求。试 constrained-baseline 与兼容 High 配对，核实 packetization-mode、level、最大宏块率及真实码流 | 对外公布实际可发送格式；无共同格式时在用户授权的备选格式中重协商。显式固定分辨率/FPS 不达标时提供可选档和原因 |
| VP9 | 先在浏览器能力交集中对照 H.264；逐设备测编码耗时、解码功耗、文字/运动质量，SVC 检查实际支持的 scalabilityMode | 低码率可有收益，软编或软解耗时可能吃掉一帧预算。原生新增需成熟 RTP packetizer、协商和恢复测试 |
| AV1 | 只在双方实际编码/解码和持续实时测试通过时开放；记录硬件代际、空间/时间层、关键帧恢复 | 相同观感节省的码率必须覆盖额外编码耗时和实例成本 |
| HEVC | 单独验证桌面、WebView 和具体浏览器对 WebRTC 的 offer/answer、RTP 封装、实际解码及分发条件。仅对通过组合启用 | 本机播放器能播放 HEVC 只证明文件播放能力；浏览器 WebRTC 能力需独立验收。H.264 作为共同兼容路线。[WebRTC 视频互操作基线](https://www.rfc-editor.org/rfc/rfc7742) |

**参数与恢复。** 第一套互动基线请求 B=0、关闭 lookahead、低延迟率控和短 VBV；验证参数是否接受，并从编码时间戳、在途深度和峰值包速率核对实际行为。用 1–2 秒 GOP 对比现有不同模式的 GOP，按需 IDR 优先于固定周期，不让多个新观众重复触发大帧。VBV 太小会破坏场景切换，过大则推高排队，按高运动主观质量、短时峰值和帧龄联合选择。码率热改先测实际输出收敛；需重建时以新代次首个参数集+IDR 原子切换，失败继续同格式可用路径或终止并报原因。测驱动拒绝、GPU 满载和会话额度耗尽。

## 6. 高动态画质与自适应

现有 Web 自动码率预算按每百万像素每帧计算。在 1080p60，motion 约 **8.71 Mbps**，detail 约 **14.93 Mbps**；两者均为上限。Web 的 detail/balanced 都提示保分辨率；当前 balanced 没有内容分类器。建议保留用户选项与历史 `ev.screenShare.*` 偏好，独立显示“请求”“生效”“限制原因”。手动固定模式只在用户允许的维度内调整；变更许可范围需用户明确选择。上限同步约束 UI、偏好加载和原生/API 边界。[现有预算与模式](../../apps/desktop/src/lib/screenShareSettings.ts)

| 模式 | 信号与动作 | 重点评测 |
|---|---|---|
| 清晰度优先 | Web `detail` + `maintain-resolution`，原生保像素预算、干净边缘和等比缩放。先调码率、再在授权范围内减少更新频率；静止时无需制造 60 个重复帧，变化后的首帧仍须及时 | 彩色代码、小字、细线，以及滚动停止后恢复清晰所需时间 |
| 流畅度优先 | Web `motion` + `maintain-framerate`，原生优先保持帧节拍。试提高运动码率上限、暂停过期原始帧、按观看者选低层；稳定过载才改变已获许可的空间分辨率 | 60 FPS 游戏回放、平移、大片纹理更新、转场后块效应、重复帧与 P99 帧间隔 |
| 智能自适应（实验） | 原生优先用 dirty 面积、低频 GPU 缩略差分、单位像素输出比特、可用时的 QP；Web 优先用帧变化率、encoder stats、qualityLimitationReason 和接收反馈。无可靠内容指标时沿用用户基础模式。避免逐帧整图 CPU 读取 | 文字覆盖在运动背景，低延迟地识别过载；用文字↔游戏切换验证不来回跳档 |

**闭环分三层。** WebRTC 负责包级拥塞控制。应用按观看者约每秒采样一个独立窗口，使用新鲜 BWE、实际吞吐、RTT 趋势、区间丢包/重传、pacer 驻留和接收解码/冻结；发布端另看全体上行预算、每层编码 P95、纹理池耗尽和源帧率。遇到本地编码饱和先处理编码负载，看到单观众解码慢先为该观众降层，只有总上行或共同编码资源受限时才动高档。接收信息走低频、可丢的诊断反馈；不能提供的字段携带缺失标记和时间，决策可退回现有 REMB/本端证据。

**建议起测参数。** 延用现有 85% / 95% 分层迟滞作对照：新策略按 1 秒窗口，连续 2 次可用预算低于当前层需求或帧龄超标则降层；硬性积压即时丢弃过期工作。恢复后连续 5 个健康窗口、至少 20% 候选档余量，先小步上探码率，再请求 IDR 升一层；失败退回并延长冷却。短时 RTT 抬升或静态低码率单独出现不触发切中继或降分辨率。记录每次决策的输入、阈值、层与原因，按阶跃限速→恢复曲线对比震荡次数、恢复耗时和强端质量。

## 7. 低延迟传输、接收与音画同步

**预算单位是帧龄。** 60 FPS 每帧间隔 16.67 ms。各持续流水线阶段的吞吐都要跟得上这个节拍；多阶段可以并行，但同一帧的等待会沿途累加。建议在 LAN 以采集等帧/读出 17 ms、处理编码 15 ms、发送队列 15 ms、网络 10 ms、接收驻留 40 ms、解码合成与扫描 30 ms 作第一版约 **127 ms** 的典型值分配，剩余留给调度波动。它是找超支环节的工作预算；最终 P50/P95 直接统计逐次同帧 G2G，不把各阶段独立分位数相加。

| 队列 / 时钟 | 建议的约束与过载行为 |
|---|---|
| 原始帧 → 编码 | 每层最多一个最新待编码帧，忙时旧待处理帧由新帧覆盖。用单调时钟计算队龄；在 GPU 拷贝/缩放之前尽早做节流，给最后的变化和新观看者 IDR 留例外。每次丢弃记录原因 |
| 编码器内部 | 在输入表面池限制并发，监测输入等待和提交→对应输出延迟，驱动不返回时可取消。在高低档共享设备时为高档留预算，低档不能在高档 worker 上无限阻塞。低档初始化失败按代次限次并退避；实测确定何时释放空闲实例 |
| 压缩帧 → 逐 peer 发送 | 帧数、未发送字节和最老帧龄三重限制。新互动策略先比较 2–3 帧和 30–50 ms 两种约束；大 IDR 的分包与 pacing 单独计时。原始帧可覆盖，已编码 P 帧须尊重依赖；超时丢弃失效依赖链、置等待可解码关键帧，至下个参数集+IDR 恢复。写 socket/轨超时只回收该 peer。丢弃保留媒体时间间隔 |
| RTP/RTCP | 用现有库完成分包、序号、SR/RR、NACK/RTX（协商可用时）、PLI/FIR、ICE、DTLS-SRTP。按协商结果与实包核对反馈，保留短重传历史；超过播放期限时优先恢复可解码的新画面。关键帧请求同层合并、限频并保留待处理标志，IDR 峰值进入发送预算 |
| 接收与渲染 | Web 和桌面 WebView 复用 WebRTC jitter buffer 与视频元素，不增加 JS 帧队列。先用浏览器默认和小目标做 A/B，再按抖动突发、真实驻留和冻结调目标；解码耗时上升时优先换层。读回 `jitterBufferTarget` 只代表 API 接受值。网络恢复时确认帧龄回落，需要时请求新关键帧；只有解码状态持续无进展才有限重建 |

**网络恢复。** 保留现有 ICE restart、冷却和失败重建；区分健康静态源、冻结的解码器、ICE 失败和过期 TURN 凭证。对每次观看的 watchSession/generation 限制早到候选数、字节和存活期；后台前台切换、旧 answer 和凭证轮换分别测试。自动改线路须有选中 pair 上的证据，不用低 bits/pixel 或单次解码掉帧单独判断。统计第一帧、协商耗时、故障恢复到实时画面的时间，与稳态 G2G 分开。保留手工直连/中继选择。[恢复策略](../../apps/desktop/src/lib/screenShareIceRestart.ts) · [自动线路选择](../../apps/desktop/src/lib/screenShareAutoRelay.ts)

**统一时间。** WGC 的 SystemRelativeTime 与 GDI 的会话相对时间进入同一帧泵（`main.rs:4720,5966`）；切后端时须映射到同一 QPC 域。当前视频对 >500 ms 空档压缩时间线（约 5174 行），同一共享的音频按 20 ms 样本推进。原生音频队列满时可能丢新包，后续写轨仍固定 20 ms；WASAPI 读缓冲现未取设备位置/QPC。能否产生可闻漂移需测。建议保留不可变源时间及独立媒体时钟映射；按每个 SSRC/层从同一基准映射 90 kHz 视频和 48 kHz 音频，RTCP SR 与同步 CNAME 关联，层切换保持该观看者 RTP 时间连续。冻结、丢包、静音、设备重启、后台恢复时显式处理间断，保留真实经过的时间。近似同步的浏览器播放目标也需核对真实音画偏差。

## 8. Web/Desktop 互通与共享音频

**发布契约。** Web 在安全上下文及用户操作下调用选择器，按浏览器提供的屏幕、窗口、标签页和音频权限工作。先取用户所选轨的 `getSettings()`，再对照 `applyConstraints`、各 sender 实际参数和编码尺寸；不支持 `contentHint` 或 `degradationPreference` 时保留采集、记下未应用的偏好。有共享音频请求却没有音轨时展示原因或可选的无声共享，保留用户选择。并发观看共用源，不因单人换层改全局采集约束；按所有权清理资源：停止发布时释放源 tracks，换源时清理旧源，晚到的选择器结果立即释放。Web 画中画复用主视图视频元素和 PC；退出仅解除画中画。Tauri 独立浮窗使用自己的观看订阅，只释放其订阅、PC、采样任务与音频节点。[W3C Screen Capture](https://www.w3.org/TR/screen-capture/) · [W3C WebRTC](https://www.w3.org/TR/webrtc/)

**协商契约。** 区分可枚举 codec、可配置 codec、可实时编码、对端可实时解码四个层次。Web 通过 transceiver 的 `setCodecPreferences` 排序实际可用能力，保留有效 RTX/apt 等依赖；让 offer/answer 选交集，用 `codecId` 和实际解码帧确认。H.264 比较 profile/constraints/level/packetization-mode，逐方向检查 level-asymmetry 和实发 SPS；加入只能收 constrained-baseline 的观看者时，评估新兼容编码层的预算，已有会话继续使用其已协商格式。浏览器硬件能力只记录 UA 披露的实现、powerEfficient 字段与实测吞吐；缺失记未知。Web 当前 sender 主要配置首项 encoding，未来 RID simulcast/SVC 需协商和真实多层输出验证，禁止仅凭 API 字段存在即开启。

| 产品组合 | 必测发布与观看入口 | 主要失效点 |
|---|---|---|
| Desktop → Desktop | 真 Windows WGC/MFT → 另一设备 Tauri WebView，共享音频、主视图和浮窗 | SPS vs fmtp、硬解、双显示器、浮窗切换重复播放 |
| Desktop → Web | 同一原生发送端 → Chrome/Edge、Firefox，条件允许加 Safari | High/Baseline、反馈差异、硬解缺失、TURN、远端关轨 |
| Web → Desktop | 真实浏览器选择标签页/窗口/屏幕 → Tauri WebView，全屏及音量 | 源选择、实际约束、浏览器发送 codec、无音轨、ICE restart |
| Web → Web | 同浏览器与跨引擎两机互看，换源、关页、重连 | 权限、音频可用性、降层恢复、前后台节流 |

每个组合都记录共同 codec/fmtp、实发与实显 FPS、光学 G2G、画质、起停、断网恢复、同步和长跑。共享音频与麦克风分轨、独立增益；视频元素与 WebAudio 在主窗口/浮窗交接时只有一个听得见的接收播放出口。本机预览保持静音。屏幕音频排除自身、进程树窗口音频不放宽为全系统；Web 授权标签页音频不能代表整个 OS 混音。对窗口/系统不支持排除 EchoVoice 的组合，显式说明回采风险并测试回声/重复，允许选择不采共享音频。以接收扬声器+真实显示器共同录制闪白/点击，报告 audio-minus-video 带符号偏差和每小时斜率。

## 9. 多观看者容量与 SFU 决策

原生两个人订阅同档时可复用一次编码，低档按需增加一次编码，**每人仍有独立加密出流**。现状高低档串行，实例从未创建、已创建但空闲、实际编码需分开计。Web 是每人独立 PC/sender；编码器是否底层共享、硬件实例是否回退，用引擎跟踪与 stats 验证。TURN 转发每条连接，无法消除发布者的 N 份上行；单/双分配和 TURN-over-TCP 分别标记。服务端网卡收发分别统计以免双计。

| 观看人数 | 同档每人 12 Mbps 视频的发布者视频负载（示例） | 需实测的差异 |
|---:|---:|---|
| 1 | 12 Mbps | 编码与单连接基线，进程 CPU、GPU 各引擎和首帧 |
| 2 | 24 Mbps | 同档复用、一个弱端选低层、强端保持质量及音画同步 |
| 5 | 60 Mbps | 并发硬编会话、总上行/pacer、混合直连与 TURN |
| 10 | 120 Mbps | 全员同时加入的 IDR、握手峰值、端口分配、晚加入/离开回收 |

这张表只计算视频有效载荷。实际总发送率为各观看者视频、音频、头部、控制包、重传及相关中继开销之和。5 人中 3 人选 12 Mbps 高档、2 人选 3 Mbps 低档时，视频为 42 Mbps；列出每人的数据才看得出哪条链路受限。SFU 部署后发布者发已选择的层集合，服务器向 **N 个观看者** 各发其订阅层，同时增加一跳、运维和新的媒体信任边界。

**容量判据。** 以 1/2/5/10 位独立接收终端（或明确标注的负载机）重复同一回放，分别测全直连、混合、全中继和一弱多强。逐人检查第 12 节的 FPS/G2G/冻结门槛，标记第一个持续超标的资源及最大可通过 N；小样本档间可在拐点补测。只有目标场景多次因发布者总上行或 Web 多路编码首先失败、且自建服务器有相应出口与信任条件，才评审可选 SFU。当前证据不足以给出“从第几人必须上 SFU”。

## 10. 调试面板与远程协助

**可开关的共享诊断。** 复用观看工具栏、设置页与浮窗样式，按源、编码层和观看者显示；新增文案进入 en-US / zh-CN，本地偏好进入 `ev.*`。轻量环形计数器常驻，展开时按约 1 Hz 取增量，详细 trace 按次启用并设置容量和时限。展示请求/实测、单位、时间窗、数据来源及“平台未提供”。隐藏页、SSRC 重置、计数器倒退和无新帧分别标记。现在的前端 `framesDecoded` 增量是解码 FPS，零增量沿用旧值会掩盖冻结；面板应区分有效窗口内的零帧、最后一帧年龄及未知。发送端约 2368–2383 行把缺失的编码耗时/重传数填零、缺失的受限原因填 none、输出尺寸回退到源轨尺寸，重构时保留这些字段各自的来源和有效性。[现有观看统计](../../apps/desktop/src/lib/screen-share-transport.svelte.ts)

| 观测点 | 面板与导出字段 | 口径 |
|---|---|---|
| 源与 GPU | 到帧/有效变化/节流后 FPS，采集回调耗时，GPU copy/转换耗时与次数、尺寸、色彩、CPU/显存/编解码引擎负载 | 原生 QPC、GPU timestamp/ETW；浏览器若有 media-source 数据则标注来源，`getSettings().frameRate` 只列配置 |
| 编码与发送 | 各层提交/实际产出/实际发出 FPS、输入→对应输出耗时、码率、关键帧尺寸、编码器类型、队列长度/字节/最老年龄、按原因丢弃 | 原生逐帧 ID 配对；浏览器用 ΔframesEncoded、ΔframesSent、ΔtotalEncodeTime/ΔframesEncoded、ΔbytesSent/Δt。首帧、最近一次与分位数分列 |
| 链路 | SDP 协商结果、selected pair 双端候选类型、RTT、jitter、区间丢包、有效/线路码率、BWE、NACK/PLI/FIR/RTX、pacer 等待、重连/切层原因 | 优先 transport.selectedCandidatePairId；回退推断须标注。按 SSRC 分窗，媒体吞吐与协议开销分口径，单向网络延迟要求校时，RTT/2 不作为样本 |

统计只允许用支持该指标的原始对象推导。JS 看不到的硬件队列、端到端网络单程和真实显示扫描，面板标未知，实验室另测。不同设备的单调时钟不可直接相减。导出版本、环境、策略决策及匿名会话关联，避免记录桌面像素、按键内容和 TURN 凭证。[W3C WebRTC Stats](https://www.w3.org/TR/webrtc-stats/)

**远程协助作为附属模块。** 第一阶段继续使用已经部署的控制平面和 WS 输入。Go 已校验控制者身份、控制状态、递增序号、速率与本地输入优先窗口；Windows 负责目标边界、注入及释放。当前待批准时限 60 s、活跃租约 10 s、本地优先 3 s；需测试断线即停输入与租约过期兜底的区别。控制者可为 Web 或 Windows，被控端限 Windows。停止观看、换源、撤销、共享结束、宿主本地操作或断线时，立即停止接纳对应输入并释放已按下状态，重连需新申请。窗口坐标按实际内容矩形换算，包含黑边、DPI 与窗口移动测试。异常进程退出无法依赖析构执行，需在验证中区分正常关闭、连接丢失和宿主硬退出，评估宿主外的本地守护释放是否必要。[服务端授权](../../services/ev-server/internal/api/remote_control.go) · [Windows 宿主](../../apps/desktop/src-tauri/src/remote_control.rs)

只有 WS 延迟或争用实测影响控制时才评估独立 DataChannel。通道绑定已批准的 controlId、shareId、peer/设备、watch generation、到期时间与权限范围；宿主独立核验并监听撤销，授权状态中断即停。指针移动仅保留最新态，键/按钮边沿和 release 可靠有序；点击携带关联坐标，跨通道乱序不改变点击位置。设置 bufferedAmount 限额，过载释放输入并结束控制会话，视频继续。批准、撤销与审计仍由服务器管理。A/B 比较控制关闭与高频输入时视频 FPS、P95 帧龄和音频连续性。

### 11.2 台架与素材

1. **真实媒体链。** 两台独立设备，分别记录分辨率、刷新率、缩放、显示处理模式、Windows/浏览器/WebView/驱动版本、GPU LUID、硬件加速状态、电源计划和温度。标定实际源能持续产出 60 个不同帧，接收屏刷新率至少 60 Hz。全套产品路径用真实选择器/WGC；可控图案只作为输入。CI 可跑合成分支并把它标为功能回归。
2. **八类输入。** 固化时长、分辨率、色域、素材哈希和生成种子。包括①静态桌面加稀疏光标，②固定字号中英代码/彩色细线，③已知像素速度的滚动网页，④本地无损参考或有原片的 1080p60 视频，⑤可回放输入的 60 FPS 游戏，⑥固定轨迹快速旋转的 3D 相机，⑦草地/网格等高纹理场景，⑧全屏运动+代码叠加、明暗场景硬切。记录原始渲染帧号，避免把不稳定的测试源计为编码掉帧。
3. **画面对齐与画质。** 每帧边缘嵌入可读序号；在单独质量轮次无损采集接收画面，按序号配对、裁去黑边和标记区，统一尺寸、色域、range 和 chroma siting，再算 PSNR/SSIM，可加 VMAF。漏帧、重复、重排独立计分，不能悄悄删掉最差的时间段。静态看可读字/彩边，运动看纹理和块效应，切镜看恢复清晰的时间/最差帧；同码率盲评和同观感所需码率都报告。
4. **真实 G2G 与音画同步。** 让同一高速相机同时拍源屏和接收屏的同一扫描区域，源显示唯一帧号和不规则闪白，逐事件匹配首次发光的帧号差。建议 ≥240 fps，约 4.17 ms/相机帧，报告量化、滚动快门和显示刷新误差；用同一画面或光电探头校验台架。网络整形可让两块屏并排而媒体走 WAN/TURN。异地真公网需同步的采集设备和误差界，否则只报告阶段指标。同步测试让同帧产生音频脉冲，以同一采集设备摄录接收屏和扬声器，校准麦克风距离及录音固定延迟。
5. **网络矩阵。** 受控中间网关按方向整形，保存队列类型、容量、实际 RTT/吞吐、丢包分布、种子与双向路由。LAN 直连无注入；良好公网基准 RTT 40/80 ms、丢包 0–0.8%、足够上行，并补真实公网；高 RTT 150/250 ms、低抖动；轻丢包 0.5/1%；3% 随机及同均值突发丢包；独立注入单向 0–30 ms 抖动；上行例如 25→6→2→25 Mbps；强制实际 TURN，核验选中 pair。TCP 中继、上下行不对称、短断网和 ICE restart 分列。改变 RTT 时记录两方向引入的延迟，避免两端重复整形。
6. **重复和控制变量。** 在相同提交基线/候选、硬件、真实观众数、素材、编码档、网络配置下随机交替 A/B。建议每组预热 30 s，稳定段 120 s，至少 5 次，多次测量不稳定时增加轮数；冷启动/切层/网络切换单列。G2G 每条件至少 100 个可配对事件，公布各轮分布及按轮重采样区间。保存未捕获事件比例，卡住的帧以超时/冻结计入。占用和 G2G 对测试工具开销敏感，区分开启/关闭录屏与诊断的轮次。

### 11.3 同口径报告

每行唯一标识为提交、用例、两端设备、编解码器、人数、路径、素材、网络和轮次。交付基线/候选/差值及单位，附原始统计、网络配置、帧号匹配表、盲评表与失败日志。分别统计采集/编码/发送/接收/解码/实际呈现 FPS、呈现帧间隔 P95/P99、G2G P50/P95、A/V 有符号偏差和斜率、首次出画与恢复耗时、各层码率与 IDR 峰值、队列年龄、重复/丢帧/冻结、CPU/GPU 分引擎/显存、发送端与 TURN 实际收发流量。端点无法导出的指标明确写原因和替代观测；同机 RTT、浏览器回调或理想化估算均不能填入 G2G 栏。

**回滚粒度。** 采集后端、编码输入路径、接收策略和自适应策略各自可切换，避免一次试验同时改变四个变量。兼容回退只能选择满足当前权限和质量约束的路径；改变来源范围、固定档位或音频权限须明确告知并由用户选择。配置修改分别记录下次共享生效与会话内生效，旧客户端忽略可选诊断字段。评审通过前不引入协议、schema 或用户配置改动。

**工程质量门。** 进入实施后，每个模块先跑最窄的相关测试，再运行受影响包构建。前端交互走现有 workspace 浏览器测试和真实选屏互通；Rust 媒体改动执行 `cargo fmt --all -- --check` 及相关 Rust 测试；Go 变更在 `services/ev-server` 执行 `go test ./...`。浏览器不可用导致的 skip 单列。当前交付停在第一轮架构评审，下一轮的起点是阶段 A。
