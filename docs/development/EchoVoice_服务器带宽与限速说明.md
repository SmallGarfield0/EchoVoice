# EchoVoice 服务器带宽与限速说明

面向「服务器有没有限速、能不能把带宽吃满」这个问题。结论先行，再给依据与实测。

## 一句话结论

EchoVoice 的语音与屏幕共享**都是 P2P WebRTC，服务器不承载媒体**。
服务器上唯一会消耗媒体带宽的是 **TURN 中继**（两端都无法直连时才发生）。
所以「服务器限速」这件事在代码里**不存在可关掉的开关**：没有带宽限速器，也没有码率上限。
真正能卡住你的只有三件事，都已改为可配置：**信令消息大小**、**中继端口池**、**信令队列深度**。

## 数据是怎么走的

| 路径 | 经过服务器吗 | 服务器消耗 | 单观看者 1080p30 参考 |
| --- | --- | --- | --- |
| 直连（host / srflx 打通） | 否 | 仅信令（几 KB/次） | 0 |
| TURN 中继（`turn:` 候选） | 是 | 一份上行 + 一份下行拷贝 | ≈ 4.4 Mbps |
| Web 端屏幕共享（N 观看者） | 否* | 仅信令 | 每人一份独立编码 |

\* Web 端共享时浏览器各有独立编码器，服务器同样不参与媒体。

中继时服务器出口 ≈ 每个中继观看者 `码率 × 2`（收 + 发）。10 个 4.4 Mbps 中继观看者
约 88 Mbps 服务器出口带宽，这是自建服务器时唯一需要按人数估算的量。

## 三处真正的天花板（均已可配置）

### 1. 信令消息大小 `websocket.max_message_kb`

`internal/ws/hub.go` 之前没有调用 `SetReadLimit`，而 `nhooyr.io/websocket` 的默认值是
**32768 字节**：一条携带完整 SDP 的消息超过 32 KiB 时，库会以 `1009` 直接关闭信令 socket，
表现为「协商到一半整个连接没了、画面永远不出现」。默认已改为 1024 KiB，`-1` 表示不限制。

`websocket.max_message_kb: 1024   # 单位 KB；-1 关闭上限`

注意：这不影响媒体带宽，只是别再让它在协商中途断线。

### 2. 中继端口池 `rtc.turn.relay_min_port` / `rtc.turn.relay_max_port`

每个中继连接占一个 UDP 端口。旧默认 `49160-49200` 只有 **41 个端口**，大约 20 个中继
参与者之后 `Allocate` 就开始失败（表现为「有的人怎么都连不上，换个网络又好了」）。
新默认 `49160-49460`，共 **301 个端口**，即最多约 300 个并发中继连接。
需要更多人时按 `+2 × 中继人数` 继续放大端口范围，并在防火墙放行整段 UDP。

```yaml
rtc:
  turn:
    relay_min_port: 49160
    relay_max_port: 49460   # 301 个端口 = 约 300 个并发中继连接
```

### 3. 信令队列深度 `websocket.send_queue` / `websocket.priority_queue`

队列满时 hub **静默丢弃**事件（`select` 的 `default` 分支）。一次屏共享协商会连续产生
offer、answer 和十几个候选，默认已从 256/512 提到 1024/2048。若服务器承载大量并发协商
（例如几十人同时开始共享），可以继续放宽。

## 实测（本机 loopback，单核发送）

`go test ./internal/mediarelay -run TestEmbeddedTURNRelayThroughputAndCapacity -v`

| 指标 | 实测 |
| --- | --- |
| 单个中继连接传输能力 | **≈ 565 Mbit/s**（1 秒传 67 MB，1.2 KB/包） |
| 送进中继 vs 送达 | 86.4 MB → 67.4 MB（78%，差值主要是发送侧压满后的 UDP 丢包） |
| 端口池容量 | 16 端口范围下：测量用 2 个 + 再接受 12 个，第 15 个起 `508` 失败 |

结论：**带宽不是瓶颈，端口池才是**。单个中继连接能跑 500+ Mbit/s，而一路 1080p30 只要
4.4 Mbps，因此一台机器能不能撑住，取决于端口数量与 CPU（中继是用户态转发），不取决于
服务器有没有限速。

## 压测方法

1. 端口池容量：把 `relay_min_port`/`relay_max_port` 设成目标范围，让 N 个人从中继观看，
   观察日志里是否出现 `Allocate error response (error 508)`——出现即端口不够。
2. 出口带宽：`nload` / `iftop` 看服务器网卡出口，对照「中继人数 × 码率 × 2」。
3. 直连比例：客户端状态行会显示 `直连` / `中继`，面板显示 `N/M 走中继`。直连比例越高，
   服务器带宽越省。
4. 客户端本身没有码率硬上限（原生发送端默认上限 22 Mbps，可在共享面板改），
   因此把服务器带宽吃满的第一步是**确保尽量多人走直连**，第二步才是加端口与带宽。

## 相关配置速查

| 键 | 默认 | 作用 |
| --- | --- | --- |
| `websocket.max_message_kb` | 1024 | 单条信令消息上限，`-1` 不限制 |
| `websocket.send_queue` | 1024 | 普通事件队列深度 |
| `websocket.priority_queue` | 2048 | 优先级事件（`rtc.signal`）队列深度 |
| `rtc.turn.enabled` | true | 是否提供中继 |
| `rtc.turn.relay_min_port` / `relay_max_port` | 49160 / 49460 | 中继端口范围 |
| `rtc.turn.tcp_enabled` | true | 是否同时开 TCP 中继 |

环境变量前缀为 `EV_WS_*` 与 `EV_TURN_*`，与上表一一对应。
