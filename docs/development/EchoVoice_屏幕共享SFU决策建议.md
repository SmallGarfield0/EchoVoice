# 屏幕共享：上不上 SFU（对比与决策材料）

本文回答一个问题：**屏幕共享要不要改成 SFU（服务端转发媒体）**，以及两种选择在
「用户体验 / 自建服务器 / 风险 / 性能消耗」四个维度上分别意味着什么。

它是决策材料，不是实施计划。文中数字只有两类：本机实测（标了命令），或明确写成估算。
前 87 轮的逐条改动见 `EchoVoice_屏幕共享优化现状.md`；传输层整体判断见
`EchoVoice_网络传输层评审与优化建议.md`。

---

## 0. 一句话结论

**人少（1–2 人看）时两种方案的用户体验几乎没区别，mesh 还少一跳；3 人以上开始分叉，
mesh 受共享者上行和编码器数量的物理限制，SFU 受服务器带宽和信任边界限制。**

决定点不是「哪个更先进」，而是：**你的典型场景里，同时看共享的人有几个，共享者的上行有多大。**

---

## 1. 用户体验差异

### 1.1 按人数看（1080p30 屏共享，按本项目 auto 码率约 4.4 Mbps/人估算）

| 同时观看人数 | mesh（现状） | SFU |
| --- | --- | --- |
| 1 人 | 完全够用，且少一跳，延迟最低 | 多一跳（同城 5–15 ms，跨城 20–50 ms），体感无差 |
| 2 人 | 上行约 8.8 Mbps，家庭宽带可承受；Web 共享者要跑 2 个编码器 | 上行约 4.4 Mbps，服务器出口约 4.4 Mbps |
| 3 人 | 上行约 13 Mbps，接近多数家庭上行的一半；弱观看者开始拖累（原生单编码器取最小值） | 上行仍是 4.4 Mbps，不随人数增长 |
| 5 人 | 上行约 22 Mbps，多数家庭上行被打满 → 所有人都糊；Web 共享者 5 个编码器 | 上行 4.4 Mbps，服务器出口约 17.6 Mbps |
| 8 人以上 | 基本不可用（上行 35 Mbps+，Web 共享者 8 个编码器） | 上行 4.4 Mbps，服务器出口约 31 Mbps |

### 1.2 不随人数变化的三条体感差异

| 场景 | mesh | SFU |
| --- | --- | --- |
| 一个链路差的观看者进来 | **原生**：单编码器取所有人 REMB 最小值，全场跟着糊一次；**Web**：每人独立编码器，只影响他自己 | 每订阅者独立码率，只影响他自己 |
| 点「观看」到出画面 | 直连 177–719 ms（实测 5 次），中继 1263–1266 ms（实测 3 次） | 预计 200–500 ms（**未实测**；省掉了每观看者新建 PC 的 ICE 竞态） |
| 某人网络切换后恢复 | 观看端请求 ICE 重启，2.5 s 内不成就整条连接重建（编码器与关键帧节奏重置） | 发布端连接不变，观看端重新订阅即可 |
| 共享者改画质 | Web 实时生效；原生只能实时改**码率与帧率**，分辨率要下次共享 | 同样受发布端编码器约束，但可按订阅者下发不同层（simulcast/SVC） |

### 1.3 局域网 / 同城场景

这是 mesh 唯一**明确更优**的场景：两人同办公室或同城，直连 RTT 常在 10 ms 以内，
SFU 反而要绕一趟服务器。实测直连首帧中位数约 683 ms，主要成本是协议握手而非距离。

## 2. 自建服务器时的差异

| 维度 | mesh（现状） | SFU |
| --- | --- | --- |
| 新增组件 | 无。复用现有 `ev-server` + 内置 Pion TURN | 一个独立媒体服务（LiveKit / mediasoup / 自研 Pion SFU），要自己的进程、配置、健康检查、升级路径 |
| 端口 | TURN 需要 **UDP 3478 + 49160–49460 共 301 个中继端口**（这是当前并发中继上限），且只监听 IPv4 | 通常**一个 UDP 端口**（常放 443/udp 以便过企业防火墙），TURN 只在极端 NAT 下兜底 |
| 服务器带宽 | 只有走中继的观看者占带宽，且是**按观看者线性**（每人一份） | **所有**观看者都占服务器出口：(N−1) × 码率。10 人 1080p30 ≈ 40 Mbps 持续 |
| 服务器 CPU | 极低（只转发加密的 STUN/TURN 字节，不解码） | 低（不转码时是纯转发）；一旦要对弱端降码率就得开 simulcast/SVC 或转码，成本立刻上升 |
| 月流量 | 中继用户数 × 码率 × 时长 | 全部观看者 × 码率 × 时长。40 Mbps 持续一小时 ≈ 18 GB |
| 部署复杂度 | 低：一条防火墙规则组 + 一个已有的 Go 进程 | 中：多一个服务、TLS 证书、可能的集群/级联、监控与告警 |
| 水平扩展 | 难：中继端口池绑定单机 | 较易：多实例 + 房间调度（但需要一致性路由） |
| 与现有代码的关系 | 已就位 | 需要新增 publish/subscribe 信令、客户端拓扑切换、mesh 回滚开关 |

**一句话**：mesh 把成本推给共享者的上行，SFU 把成本推给服务器出口和运维。

### 2.1 成本量级（按常见 VPS）

- 3 人场景：mesh 省服务器带宽；SFU 约 8.8 Mbps 出口，几乎无感。
- 10 人场景：SFU 约 40 Mbps 出口。按 1 TB/月 流量包计算，约 **25 小时** 就会用完。
  这是 SFU 最容易被低估的一项成本。
- 若只让「3 人以上」走 SFU、1–2 人走 mesh（推荐的混合形态），日常小会几乎不产生服务器出口。

## 3. 风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **媒体在服务器明文可见** | mesh 下服务器只转发加密的 TURN 字节，看不到画面；SFU 必须解码不了也能读到明文 RTP（SRTP 由 SFU 终结） | 服务器级开关 + 明确隐私说明；只让「屏幕共享」走 SFU、语音保持 P2P |
| 单点故障 | SFU 挂掉 → 所有观看者同时断；mesh 下只有中继用户受影响，直连用户无感 | 多实例 + 客户端自动回落到 mesh |
| 拓扑两套、测试翻倍 | 现有 96 轮的验证资产（真实浏览器互操作门、23 个单测套件）全部针对 mesh | 保留 mesh 路径并加开关，两套都进验收门 |
| 中继端口池瓶颈被掩盖 | 现已从 41 个上调到 301 个，端口不再是首要瓶颈；但 SFU 自身的连接数/C 端口也要规划 | 显式列出端口与容量表 |
| 编码器与自适应复杂度 | 若用 simulcast，共享者要同时编 2–3 层（CPU 上升）；若单层下行，弱端仍会糊 | 先做单层 + 每订阅者码率上限，再评估 SVC |
| 迁移期行为不一致 | 旧客户端不认识 SFU 信令 | 信令协商降级：不支持就走 mesh |
| 隐私合规 | 企业内部会议可能禁止媒体经服务器 | 保留「强制 P2P / 仅中继」策略开关，和现在的 `relay_mode` 构想一致 |

## 4. 性能消耗对照

| 指标 | mesh（现状） | SFU |
| --- | --- | --- |
| 共享者上行 | **N × 码率**（N = 观看者数） | **1 × 码率**（simulcast 时 2–3 ×） |
| 服务器出口 | 仅中继观看者：M × 码率 | 全部观看者：(N−1) × 码率 |
| 共享者编码器数量（Web） | **N 个**（每观看者一路） | 1 个（或 2–3 层） |
| 共享者编码器数量（原生） | 1 个（多队列扇出，引用计数 O(1)） | 1 个 |
| 观看者下行 | 1 × 码率 | 1 × 码率 |
| 首帧 | 直连 177–719 ms；中继 1263–1266 ms（实测） | 预计 200–500 ms（未实测） |
| 端到端延迟 | 直连最少（无中间跳） | 多一跳 |
| 弱观看者对他人影响 | 原生：全场；Web：仅本人 | 仅本人 |
| 服务器 CPU | 可忽略 | 低（转发）；开转码后显著 |

## 5. 三条可选路线

### A. 继续 mesh（现状 + 已做的提示）

适合：典型场景是 1–2 人看共享，或主要在局域网/同城。

成本：0。已落地的东西（见 `EchoVoice_屏幕共享优化现状.md`）：路径可见性（直连/中继）、
上行估算与警告、码率上限、原生实时改码率与帧率、自适应播放缓冲。

天花板：**3 人以上上行 = N × 码率**，这是物理上行的乘法，代码改不动。

### B. 全量 SFU

适合：经常 3 人以上一起看，且愿意承担服务器带宽与运维。

成本：自研 2–4 周（含每订阅者码率适配），接现成 SFU 3–6 周（含学习与集成）。
必须同时做：mesh 回滚开关、隐私开关、端口与容量表、两套拓扑的验收门。

### C. 混合（推荐形态）

**观看者 ≤ 2 走 mesh，≥ 3 自动切 SFU**，语音始终走 P2P/现有 mesh。

好处：日常小会零服务器成本、零额外延迟；大会自动获得线性上行。
代价：两套拓扑都要维护，切换点要可观测（UI 显示「当前为直连/中继/服务器转发」）。

---

## 6. 如果决定做，验收标准（建议）

1. 5 人 1080p30：共享者上行 ≤ 1.2 × 码率，服务器出口 ≤ 4 × 码率。
2. 5 人场景首帧 ≤ 800 ms（p90）。
3. 一个观看者丢包 10% 时，其余观看者的码率下降 ≤ 10%。
4. mesh 开关可一键回退，回退后行为与今天完全一致。
5. 隐私开关关闭媒体转发时，UI 明确显示「本场仅 P2P」。

## 7. 我们手上的实测数字（供核对）

全部来自本机真实浏览器互操作测试，命令见 `screen-share-troubleshooting.md`：

| 指标 | 直连 | 本机 TURN 中继 |
| --- | --- | --- |
| 首帧（多次采样） | 177 / 213 / 683 / 685 / 719 ms | 1263 / 1264 / 1266 ms |
| 候选收集 | 44–49 ms | 103–120 ms |
| ICE 连通 | 59–68 ms | 165–197 ms |
| DTLS 完成 | 70–279 ms | 1160–1167 ms（受 1 s 提名闸门主导） |
| 解码帧率（1280×720@30） | 30.0–31.0 fps | 30.0 fps |
| p95 帧间隔 | 50.1 ms | 50.1 ms |
| 丢帧 | 0 | 0 |

服务端两条硬限制（`services/ev-server`）：

- 中继端口池 `49160–49460`，共 **301 个**并发 allocation（2026-11-13 从 41 个上调，实测带宽
  不是瓶颈、端口才是）；每个观看者一条 PC，一场 8 人共享要吃掉 5–8 个。
- TURN 只监听 `udp4/tcp4`，IPv6 用户全部落到 IPv4 中继或直连失败。

SFU 会绕开这两条：服务端与每个客户端只有**一条**连接，端口需求从 O(观看者²) 降到 O(参与者)。

## 8. 如果走混合形态：自建服务器要配什么

> 这一节是**规划**，不是现状。下面带 `sfu:` / `screen_share:` 的配置项目前在
> `ev-server.yaml` 里都不存在；现状只有 `server` / `web` / `storage` / `relay` / `rtc` 五段
> （见 `EchoVoice部署文档.md` 第 7 节）。

### 8.1 今天就要配的（混合形态不改变）

混合形态里 1–2 人仍然走 mesh，所以现有这套配置**一个都不能少**：

```yaml
server:
  public_url: https://voice.example.com:17878   # 必须是客户端可访问的外部地址
  password: "高强度服务器密码"
  tls:
    enabled: true
    cert_file: ./certs/fullchain.pem
    key_file: ./certs/privkey.pem
rtc:
  turn:
    enabled: true
    public_host: voice.example.com              # 必须是能解析到本机的公网 IPv4
    port: 3478
    relay_min_port: 49160
    relay_max_port: 49460
    tcp_enabled: true
```

对应的防火墙（现状即可用）：

| 端口 | 协议 | 用途 |
| --- | --- | --- |
| 17878 | TCP | HTTP/HTTPS API、WSS 信令、Web 静态资源 |
| 3478 | UDP + TCP | STUN / TURN |
| 49160–49460 | UDP | 中继媒体（**共 301 个**，也就是 301 个并发中继连接） |

### 8.2 混合形态新增的三块

**(1) 一个 SFU 服务。** 它可以是同机进程、独立机器，或托管服务。同机部署最省事，也最容易
被共享者上行以外的带宽问题卡住（见 8.4）。

**(2) `ev-server.yaml` 新增两段**（命名是建议，实现时会定稿）：

```yaml
sfu:
  enabled: true
  # 客户端拿到的媒体地址；同机部署就是 voice.example.com
  public_host: sfu.example.com
  # 信令端口：客户端先连这个地址拿 token / 加入房间（走 WSS）
  ws_url: wss://sfu.example.com:7880
  # 只监听本机回环，媒体端口由 SFU 自己对外
  api_key: "与 SFU 服务端一致的 key"
  api_secret: "与 SFU 服务端一致的 secret"
  # 媒体端口范围（LiveKit 默认 50000–60000/udp；也可只开 443/udp）
  media_port_min: 50000
  media_port_max: 50200

screen_share:
  # auto = 观看者 ≤ 阈值走 mesh，超过阈值走 SFU
  relay_mode: auto
  auto_sfu_viewer_threshold: 3
  # 隐私开关：false 时永不把媒体交给服务器，超过阈值就只提示「可能卡」
  allow_server_relay: true
  # 每观看者下行上限，保护服务器出口
  per_viewer_max_bitrate_kbps: 8000
```

**(3) DNS 与证书。** 如果 SFU 与 ev-server 不同机，需要一个额外主机名
（如 `sfu.example.com`）；`ws_url` 走 WSS 就必须有该域名的有效证书。
媒体本身是 DTLS-SRTP，不需要额外证书，但需要 UDP 端口可达。

### 8.3 端口表（混合形态）

| 端口 | 协议 | 用途 | 相对现状 |
| --- | --- | --- | --- |
| 17878 | TCP | API / WSS / Web | 不变 |
| 3478 | UDP + TCP | STUN / TURN（语音、1–2 人共享） | 不变 |
| 49160–49460 | UDP | 中继媒体 | 不变（仍会被语音和小编号共享用到） |
| 7880 | TCP | SFU 信令（WSS） | **新增** |
| 7881 | TCP | SFU 的 WebRTC over TCP 兜底 | **新增**（可选） |
| 50000–50200 | UDP | SFU 媒体 | **新增** |

如果把 SFU 媒体收敛到 **443/udp**，企业网穿透会明显更好，代价是要独占 443（不能同时给
HTTPS 用），通常需要 SFU 独占一台机器或一个 IP。

### 8.4 带宽与容量怎么估

只算 SFU 这一段（mesh 那段仍按现状）：

```
服务器入向 ≈ 1 × 码率                    （共享者上传一份）
服务器出向 ≈ (N − 1) × 码率              （每个观看者一份）
```

按 1080p30 ≈ 4.4 Mbps：

| 同时观看 | SFU 入向 | SFU 出向 |
| --- | --- | --- |
| 3 人 | 4.4 Mbps | 8.8 Mbps |
| 5 人 | 4.4 Mbps | 17.6 Mbps |
| 10 人 | 4.4 Mbps | 39.6 Mbps（约 18 GB/小时） |

CPU：纯转发不解码时，1–2 vCPU 足以支撑十几路 1080p；一旦开启 simulcast（共享者要编 2–3 层）
或服务端录制/转码，CPU 与磁盘会立刻变成主成本。

### 8.5 三份配置必须一致的地方

| 配置项 | 出现位置 | 不一致的后果 |
| --- | --- | --- |
| `api_key` / `api_secret` | ev-server 与 SFU 两边 | 客户端拿不到 token，共享直接失败 |
| `public_host` / `ws_url` | ev-server 配置、DNS、证书 | 客户端连得上信令却连不上媒体，表现为「一直转圈」 |
| 媒体端口范围 | SFU 配置与防火墙 | 信令成功、媒体不通，表现为「看到对方但没画面」 |

### 8.6 最小上线清单（混合形态）

1. 现状那套配好并验证：两人直连、两人中继各来一次（`viewerPaths` 必须分别是 `direct` / `relay`）。
2. 部署 SFU，配好 `api_key` / `api_secret`，确认 `ws_url` 与证书一致。
3. 开 `screen_share.relay_mode: auto`、`auto_sfu_viewer_threshold: 3`。
4. 用三个观看者验证：前两个必须仍走 mesh（路径显示直连/中继），第三个加入后所有人切到
   「服务器转发」。
5. 关 `allow_server_relay` 再验一次：第三人加入时应提示「可能卡」而不是偷偷转发。
6. 演练回退：`relay_mode: mesh` 后行为与今天完全一致。
