# 屏幕共享性能验收

每次测试记录客户端版本、操作系统、浏览器或 WebView2 版本、显卡及驱动、显示器分辨率和刷新率、内容模式、码率上限、接入方式、同时观看人数。编码、接收解码、合成呈现和两块物理屏幕的时间各有自己的测量点。帧率达标时仍需检查分辨率、长帧间隔、冻结及运动细节。

## Windows 原生发送到 Chromium

在仓库根目录使用 PowerShell。独立可见的 Chromium 窗口生成测试素材，Rust 按该窗口的唯一标题选择采集源，另一 Chromium 进程通过 WebRTC 接收。窗口需要保持可见。首次运行会编译原生测试程序。

```powershell
$env:EV_BENCH_NATIVE_WINDOW = '1'
$env:EV_SCREEN_SHARE_BROWSER_GPU = '1'
$env:EV_BENCH_SECONDS = '120'
$env:EV_BENCH_SCENE = 'motion'
$env:EV_BENCH_REPORT = Join-Path $env:TEMP 'ev-native-1080p60.json'
npm --prefix apps/desktop run test:screen-share-browser -- 42e020 1920 1080 60
```

将宽、高和 FPS 分别设置为 2560、1440、60 或 3840、2160、30/60 可复用该入口。验证原生 4K 细节需要真正的 4K 图像源和显示条件。普通互通测试沿用自身的合成源，原生窗口模式单独执行实际采集。通过 `EV_SCREEN_SHARE_TEST_BINARY` 可指定已编译的 Rust 测试可执行文件做交替对照。旧版本需在测试入口中按同一个标题选择素材窗口。结果先写 JSON，再判断帧率、路径、协商和发送状态。

- `sourceDrawFPS` 来自源窗口的实际绘制计数。操作系统可合并同一刷新周期内的更新。
- `senderSamples` 是测量窗口两端的原生累计计数。用差值除以 `elapsedMs` 的差值得到采集、经过节流、编码和单观看者媒体写入速率。进程 CPU 使用量以 `ΔprocessCpuMs / ΔelapsedMs × 100%` 表示，一个满载逻辑核计 100%。多层编码、多观看者和共享音频时，写入次数不能解释成单路视频发送 FPS。
- `pipeline` 报告应用执行的 GPU 纹理复制、CPU 回读、主编码调用及硬编驻留等计数。需要比较相同预览设置。开启发布端缩略图会发生额外回读。驱动内部资源传输需要单独跟踪。
- `decodedFps` 与 `renderedFps` 使用同一稳定窗口内的解码计数和合成器呈现计数。显示间隔分位数来自视频帧回调，主线程错过的回调也会拉长观测间隔。首次呈现时间从观看端开始建链起算，包含 ICE、DTLS 和起播。
- 结束快照在测试用例执行实时码率修改后生成。稳态有效码率必须取 `senderSamples`。字段缺失或 `null` 表示当前构建或平台没有观测值。

## 浏览器多人和运动画质

使用新的 PowerShell 会话。运行环境需支持当前项目的 TypeScript 加载方式，以及 Chromium 的 WebRTC 和视频帧回调。

```powershell
$env:EV_BENCH_SECONDS = '30'
$env:EV_BENCH_SCENE = 'motion'
foreach ($count in 1, 2, 5, 10) {
  $env:EV_BENCH_VIEWERS = "$count"
  $env:EV_BENCH_REPORT = Join-Path $env:TEMP "ev-mesh-$count.json"
  npm --prefix apps/desktop run bench:screen-share -- 42e020 1920 1080 60
}
```

每个观看者有独立的真实 WebRTC 连接。发送与接收在同机 Chromium 中运行，会争用同一套 CPU、GPU 和合成资源。报告记录每人的实际输出尺寸、码率、编码/发送/解码/呈现 FPS、冻结和渲染间隔，以及同一单调时钟内按帧号匹配的绘制至合成延迟。连接与交付成功可使 `ok` 为真，评估 1080p60 仍需单独检查每人输出 1920×1080、实际显示 ≥55 FPS。多台设备上重复相同场景才能得到部署容量。

素材包含桌面、静态文字、滚动文字、模拟 3D 镜头、复杂纹理和混合动态画面。设置 `EV_BENCH_SCENE=game` 或 `video` 并通过 `EV_BENCH_CLIP` 选择本地录制文件可播放真实游戏或视频；保持版本、文件和裁切一致。静态素材每秒产生一次变化，验收变化送达和最后一帧保持。

在独立画质轮次设置 `EV_BENCH_QUALITY=1`。源端约每 190 ms 暂存三个固定位置的 96×64 原始像素区域；接收端读取画面中 16 位帧号和校验字节，只有对应同一帧才计算。采样点在标记区之外，接收画面映射回源像素网格，以保留编码降分辨率造成的损失。报告给出匹配帧数、这些区域的亮度 PSNR 和 8×8 块 SSIM 的逐帧分位数。样本为零会使画质测试失败。该模式增加读像素开销，延迟测量使用关闭画质采样的独立轮次。原尺寸文字、色彩渐变、快速切镜及观感仍需另行检查。

## 共享音频与画面的相对时序

Web 基准设置 `EV_BENCH_SCENE=sync`。原生窗口基准设置 `EV_BENCH_NATIVE_WINDOW=1` 和 `EV_BENCH_SYNC=1`。选取至少 20 秒的测量窗口。源端以不等间隔配对亮屏与低音量的 880 Hz 短音。Web 基准直接发送生成的音轨。原生基准需要可用的 Windows 输出设备，测试窗口实际播放短音，再由生产 WASAPI 路径采集目标进程树。

接收端以视频帧回调中的预计呈现时间标记亮屏。AudioWorklet 检测解码音频中的短音，并映射到同一浏览器时钟。报告中 `audioMinusVideoMS` 为音频时间减去画面时间，正值表示音频较晚。每个亮屏在 ±650 ms 内仅匹配一个短音；同时检查亮屏、短音和配对数量。此结果覆盖软件播放链路。音箱、功放和面板扫描带来的偏差需要在物理台架上另外记录。

## 物理端到端延迟

发送端打开 `apps/desktop/scripts/screen-share-benchmark.html`，选择素材并点击全屏，使用正常产品入口共享。将发送和接收两块屏幕并排放置，用同一台高速相机录下两块屏幕的标记条，尽量让标记位于相机相同扫描行。保留原始录制的时间戳；两台机器无需对时。

```powershell
node apps/desktop/scripts/screen-share-optical.mjs recording.mkv 140,82,192,12 1130,81,168,12
node apps/desktop/scripts/screen-share-optical.test.mjs
```

两个坐标均为原始相机画面中的 `x,y,宽,高`，从左到右分别覆盖 24 个黑白单元，避开文字、边框及强反射。命令依赖可执行的 ffmpeg 和 ffprobe。工具比较两块屏上相同帧号的首次出现时间，输出 P50/P95/P99、最大值、有效配对、未配对变化、校验失败的相机帧和相机自身采样间隔。开头已经显示的值不参与配对。静止持续时间、显示刷新、滚动快门、混色和源或接收屏漏采都会影响结果，需同时公布计数、原始拍摄帧率和测量时长。合成七帧延迟的自检只校验分析工具。

局域网门槛为光学 P50 ≤150 ms、P95 ≤250 ms。良好公网为 P50 ≤300 ms、P95 ≤500 ms，需要同时记录实测 RTT、丢包、可用带宽和选中的候选对。音画同步另用同源闪白/点击，在接收端同时记录屏幕和扬声器，报告音频相对画面的有符号偏差及每小时变化。麦克风、共享音频和浮窗交接分别验收。
